## 结论速览（对方案的影响）

| 结论 | 对方案的影响 |
| --- | --- |
| ✅ SSR 样式收集可用：`vite build --ssr` + `@css-render/vue3-ssr` 的 `setup(app)` 能收集到 Naive 的样式 | `check:render` 可以用 SSR 渲染门禁（R5 解除） |
| ⚠️ **令牌值不在 collect() 的 CSS 里，而是内联在元素的 `style` 上的 CSS 变量** | `check:render` / `check:naive` 必须**同时**查 HTML 与 CSS，只查一边会得出错误结论 |
| ❌ **`inverted` 组件绕过普通主题键**，改用一批独立的默认值 | `theme.json` → `naiveTheme.ts` 必须额外产出 `*Inverted` 键；`check:naive` 白名单要点名 |
| ✅ 只覆盖 primary 时，会有 **40 处** Naive 默认色漏进产出；全覆盖后 **0 处** | R1 从"担心"变成"可量化门禁"：`check:naive` 的判据就是这 5 个默认 hex 出现 0 次 |
| ✅ `NDataTable` + `virtualScroll` 在 1000 行下只渲染 **22 个 tr**，滚动帧 p95 **16.8ms**、>20ms 帧 **0/120** | R4 解除：不需要退回自绘表格 |
| ⚠️ 行高实测 **49px**（48 + 1px 边框） | 密度令牌要按"含边框 48"实现，否则长列表每行多 1px |
| ❌ **体积是新的头号风险**：列表页 + 双壳 = **217KB gzip**，预算 250KB | 预算必须拆成"首屏路由"与"单路由 chunk"两个门禁；路由级懒加载从"可选优化"变成**硬要求** |

## Spike A —— SSR 样式收集 + themeOverrides 是否真的进产出

**问题**：`check:render` 打算改用 `@vue/server-renderer`；Naive 是 CSS-in-JS，样式能不能被收集、主题值会不会出现在产出里？

**做法**：一棵覆盖设计稿 §6.3 点名的组件树（ConfigProvider / Layout / LayoutSider(inverted) / Menu(inverted) / Card / DataTable / Pagination / Button / Tag×3 / Form / FormItem / Input / DialogProvider），跑三趟不同覆盖度的 `themeOverrides`。

| 趟 | collect() CSS | primary `#087C75` | 侧栏底 `#102E3E` | 侧栏次要字 `#B9CDD5` | `--n-height:48px` | **Naive 默认色泄漏** |
| --- | --- | --- | --- | --- | --- | --- |
| partial（只覆盖 primary） | 106,702 B | ✅（在 HTML） | ❌ | ❌ | ❌ | **40 处** |
| full（普通键） | 106,702 B | ✅（在 HTML） | ❌ | ❌ | ✅ | 0 |
| **full + `*Inverted`（修正）** | 106,702 B | ✅（在 HTML） | ✅ | ✅ | ✅ | **0** |

partial 泄漏明细：`#18a058`×5、`#36ad6a`×10、`#0c7a43`×6、`#f0a020`×9、`#d03050`×10。

**关键观察**

1. **collect() 的产出与主题无关**（三趟都是 106,702 B）—— 它给的是组件的**静态样式**，里面全是 `var(--n-*)`。真正的令牌值以**内联 `style`** 形式出现在 HTML 上。
   → 所以"查默认色有没有漏"必须查 `css + html` 两部分。
2. **`inverted` 会绕开普通主题键**。实测拿到的内联默认值：
   - `NLayoutSider inverted`：`--n-color: rgb(0, 20, 40)`、`--n-text-color: #FFF`、`--n-border-color: rgb(0, 20, 40)`
   - `NMenu inverted`：`--n-color: #0000`（透明，OK）、`--n-item-text-color: #BBB`、`--n-group-text-color: #AAA`、`--n-item-text-color-active: #FFF`
   - 只写 `Layout.siderColor` / `Menu.itemTextColor` **完全不生效**；必须写 `Layout.siderColorInverted` / `Menu.itemTextColorInverted` 等（见 `theme.spike.ts` 的 `fullOverridesWithInverted`）。
3. `--n-height: 48px` 能生效 → **触控目标 ≥48px 的要求可以在 themeOverrides 里一次注入**（`common.heightLarge`）。

**踩到的三个坑（都已落在 spike 代码注释里）**

| 坑 | 现象 | 正解 |
| --- | --- | --- |
| `setup([app])` | `TypeError: app.provide is not a function` | `@css-render/vue3-ssr` 的 `setup()` 收**单个 app** |
| `resolve.dedupe: ['css-render']` | Rollup：`failed to resolve import "css-render"` | dedupe 会强制从项目根解析；它是 naive-ui 的传递依赖，不在 `apps/web/node_modules`。**只 dedupe `vue`** |
| `server.ssrLoadModule` | `ERR_MODULE_NOT_FOUND: css-render`（pnpm 隔离布局） | 改走 `vite build --ssr` + node 执行产物（依赖全打进一个 bundle，天然单一实例） |

**复现**：`node apps/web/spike/run-ssr.mjs`（加 `$env:SPIKE_VERBOSE=1` 打印 sider/menu 的内联变量）
**原始产物**：`apps/web/spike/results/spike-a-ssr.json`

## Spike B —— NDataTable 虚拟滚动（1000 行）

**问题**：22 处长列表是本仓的硬约束；Naive 的 `DataTable` 虚拟滚动在真浏览器里的 DOM 行数与帧时间够不够？

**做法**：`vite build` → 本地静态服务 → 无头 Chrome（`--headless=new`，**关掉后台节流**）→ 通过 CDP（零依赖，Node 24 自带 WebSocket）驱动页面内 120 帧连续滚动测量。

| 指标 | 实测 | 门禁 |
| --- | --- | --- |
| 渲染总行数 | 1000 | — |
| 首帧 DOM 行数 | **22** | 虚拟化生效 |
| 滚动中 DOM 行数峰值 | **22** | 2.2% |
| 首行实际高度 | **49px** | 令牌 48 → 差 1px（边框） |
| 挂载耗时 | **20.6ms** | — |
| 虚拟内容总高 | 43,204px | — |
| 滚动帧 p50 / p95 / max | **16.7 / 16.8 / 16.8 ms** | ≤16.6ms（99 分位） |
| 超 20ms 的帧 | **0 / 120** | — |
| 页面异常 | 无 | — |

**关键观察**

1. 虚拟滚动**确实工作**（1000 行只留 22 个 `tr`），R4 的"退回自绘表格"预案不需要启动。
2. 帧时间贴着 16.7ms 的无头 Chrome 上限，p95 = 16.8ms、无一帧超 20ms —— 在**无 GPU 的无头环境**里这就是"没有掉帧"。
   > 诚实边界：这是**桌面无头 Chrome**的数字，不是中端安卓真机。设计稿 §10 的"中端机 ≤24ms"仍需 V6 用 `dumpsys gfxinfo` 在真机上量。本 spike 只证明**组件侧没有结构性卡顿**。
3. 行高 49px 而非 48px：`size="large"` 的行高不含边框，边框额外占 1px。密度令牌要按"含边框 48"表达（`box-sizing` + 边框内描边），否则长列表每行多 1px、10 行就多 10px。

**复现**：`node apps/web/spike/run-virtual-scroll.mjs`
**原始产物**：`apps/web/spike/results/spike-b-virtual-scroll.json`

## Spike C —— 体积探针（**本轮最重要的发现**）

**问题**：设计稿的"首屏 JS ≤250KB gzip"是 React + 手写组件的时代定的。换成 Naive UI 后还成立吗？

**做法**：5 次**相互独立**的 `vite build`（不是多入口共享 chunk），每次只引入一层组件集合。

| 集合 | gzip | 相对 lean |
| --- | --- | --- |
| base（vue + vue-router + pinia，无 UI 库） | **33.1 KB** | — |
| lean（ConfigProvider + Form/Input/Button/Tag/MessageProvider，≈登录页） | **88.8 KB** | — |
| lean + `NDataTable` + `NPagination` | 164.6 KB | **+75.8 KB** |
| lean + `NSelect` + `NDatePicker` | 159.3 KB | **+70.5 KB** |
| list（上两者合并 + `NDrawer`，≈一个完整列表页） | **204.7 KB** | **+115.9 KB** |
| shell（list + `NLayout`/`Sider`/`Menu`/`Header`/`Badge`/`Tooltip`，≈双壳工作台） | **217 KB** | **+128.2 KB** |

**关键观察**

1. **首屏（登录）88.8KB，预算 250KB 绰绰有余** —— 这一条不用改。
2. **但一个列表页 + 双壳就吃掉 217KB / 250KB**，而且这还没算：`NTimeline`、`NDescriptions`、`NSkeleton`、`NEmpty`、`NResult`、`NTabs`、`NDialog`、`NUpload`、`NTransfer`、`NTree`…… 以及我们自己的 25 屏业务代码。
3. 两个大头各自约 70KB：**DataTable 系**（vueuc/vooks/lodash）与 **DatePicker/Select 系**（date-fns）。
4. 结论不是"Naive 不可用"，而是**预算必须换维度**：

| 旧预算 | 新预算（实测推导） |
| --- | --- |
| 首屏 JS ≤250KB gzip（笼统） | ① **登录/首屏路由 ≤150KB gzip**（实测 88.8KB，留 60KB 余量）<br>② **任一懒加载路由 chunk ≤130KB gzip**（列表页实测增量 115.9KB）<br>③ 首屏**不得包含** `NDataTable` / `NDatePicker` |

5. **路由级懒加载从"可选优化"变成硬要求**：`NDatePicker` 只在真正需要日期筛选的屏引入（若筛选只提供"近 7 天/近 30 天"预设，可以直接不引 date-fns）。

**复现**：`node apps/web/spike/run-bundle-probe.mjs`
**原始产物**：`apps/web/spike/results/spike-c-bundle.json`

## 方案修订项（已回写设计稿）

1. §6.3 补：`*Inverted` 键清单 + `setup(app)` 单参数 + 令牌在内联 style 上。
2. §10 `check:naive` 判据落定：扫 `themeOverrides` 的字面量 + 扫 SSR/Preview 产出里 5 个 Naive 默认 hex 出现 0 次。
3. §12 DoD 第 9 条拆成 ①首屏路由 ≤150KB ②单路由 chunk ≤130KB ③首屏不含 DataTable/DatePicker。
4. §14 R1/R2/R4/R5 用实测数字替换原估计；R2 升为**高**风险；R4/R5 关闭。
5. V1-1 增加"路由级懒加载 + 按需 import + `manualChunks`"作为**必做项**。
